# odoo-pulse 1.9.0

A structural release. The package was reorganized into explicit layers and the
report logic was consolidated, with no change to what the MCP server exposes.
If you consume odoo-pulse over MCP, upgrading is a drop-in replacement.

## What changed

### Layered package structure

`src/odoo_pulse` is now split into five layers with one direction of dependency:

| Layer | Responsibility |
|---|---|
| `core/` | config, errors, cache, timeout transports, the XML-RPC client, write guards |
| `mcp/` | the FastMCP app, lazy client runtime, JSON result boundary, registry, resource adapter |
| `common/` | dates, domains, paging, schema, money, reporting, concurrency — no MCP and no global client |
| `services/` | all report business logic, grouped by department |
| `tools/` | thin `@mcp.tool()` adapters over the services |

The practical effect is that report logic is testable without an MCP app and
without a live Odoo, and a tool module is now small enough to read in one pass.

### Consolidated report and project services

Every report's business logic moved under `services/`, organized by domain:
`crm/`, `sales/`, `finance/`, `hr/`, `inventory/`, `operations/`, and
`projects/`. Previously this logic was spread across the tool modules that
exposed it, which made shared metrics hard to keep consistent.

This release also carries the project finance consistency correction — project
finance outputs now share one accounting and budget-matching policy. See
[project-finance-consistency.md](project-finance-consistency.md) for the exact
behavioural details. Some edge-case financial values are corrected as a result;
that is intended, not source-data drift.

### The MCP surface is unchanged

- **88 tools** with all groups enabled.
- **31 default tools** with the default `core,reports` groups.
- One resource: `odoo://{model}/{id}`.

No tool name, argument, default, description, input schema, resource template,
or tool-group membership changed from 1.8.2. All sixteen frozen surface
fingerprints are byte-identical.

## Compatibility note on internal module paths

**Internal Python module paths are not a compatibility API.** The layout under
`src/odoo_pulse/` — including `core`, `mcp`, `common`, `services`, and `tools`
and everything beneath them — is an implementation detail and may change in any
release. No flat compatibility shims exist for the pre-1.9.0 module paths, and
none will be added.

The supported contracts are the MCP tool surface, the `odoo://{model}/{id}`
resource, the `odoo-pulse` console entry point, and the `ODOO_*` environment
variables. If you import from `odoo_pulse` submodules directly in your own code,
pin an exact version.

## Install

Pin the exact version:

```bash
pip install "odoo-pulse==1.9.0"
```

Run without installing:

```bash
uvx odoo-pulse@1.9.0
```

Container:

```bash
docker run -i --rm \
  -e ODOO_URL=https://acme.odoo.com \
  -e ODOO_DB=acme \
  -e ODOO_USERNAME=you@example.com \
  -e ODOO_API_KEY=your-api-key \
  ghcr.io/minhhq-a1/odoo-pulse:1.9.0
```

The `1.9.0` image tag is immutable. `1.9`, `1`, and `latest` also resolve to
this release, but they move when the next release publishes — pin `1.9.0` if you
need reproducibility.

## Upgrading from 1.8.2

No configuration change is required. Your existing environment variables, tool
calls, and MCP client configuration continue to work unchanged:

```bash
pip install --upgrade "odoo-pulse==1.9.0"
```

Expect corrected values in the project-finance edge cases described above. If
you import odoo-pulse internals directly, read the compatibility note first.

### Rolling back to 1.8.2

Every channel keeps its previous exact version, so rollback is a downgrade:

```bash
pip install "odoo-pulse==1.8.2"
```

```bash
docker pull ghcr.io/minhhq-a1/odoo-pulse:1.8.2
```

The MCP surface is identical in both versions, so a rollback needs no client
change.

## Write safety is unchanged

odoo-pulse remains **read-only by default**. A write reaches Odoo only when all
four of these hold:

1. `ODOO_READ_ONLY=false` — the master switch, default `true`.
2. The target model is listed in `ODOO_WRITABLE_MODELS`.
3. `ODOO_ALLOW_DELETE=true`, required only for `delete_records`, default
   `false`.
4. `confirm=True` on the call — every write tool returns a preview struct
   otherwise.

System models such as `ir.*`, `base*`, `res.users`, and `res.groups` are
permanently blocked regardless of configuration.
