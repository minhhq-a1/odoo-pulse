## Authorization note carried over from the RC

At the time `v1.9.1rc1` and `v1.9.1` were published, the `pypi` GitHub
Environment had no configured protection rules (`protection_rules: []`), so
`publish-pypi` ran without pausing for a manual approval, both for the RC and
this stable tag. `docker.yml`'s `push_image` job had no `environment:` at all
— GHCR pushes for both `v1.9.1rc1` and `v1.9.1` went straight through the
same way, gated only by `packages: write` on the `GITHUB_TOKEN`, no approval
step. See [v1.9.1rc1-evidence.md](v1.9.1rc1-evidence.md) for the original
finding. Every tag push and workflow dispatch in this cycle (`v1.9.1rc1`,
`v1.9.1`, `publish-mcp.yml`) was individually authorized by the maintainer in
chat immediately before running, per `docs/guides/releasing.md` section 6 —
this was a real approval-workflow-in-chat, not a stand-in for the missing
environment gates.

### Fixed after this release, same day (2026-08-05)

Both gaps were closed the same day this stable release published, still
within the v1.9.1 release conversation:

- `pypi` environment: `required_reviewers` rule added (reviewer:
  `minhhq-a1`), via `gh api repos/minhhq-a1/odoo-pulse/environments/pypi
  --method PUT`.
- `docker` environment: created new, with the same `required_reviewers` rule.
  `docker.yml`'s `push_image` job now declares `environment: docker`
  (commit `4da7d00`, `ci(release): gate the GHCR push behind a docker
  environment`) so the gate actually has something to attach to. The job
  only runs `if: inputs.push_image`, so the `push_image=false` preflight
  dispatch used in section 3 of the runbook is unaffected.

Neither fix touched `src/` or `tests/`, and neither retroactively changes
what was published as `v1.9.1` — the artifacts, digests, and hashes recorded
above are unaffected. From the **next** tag onward, both `publish-pypi` and
`push_image` will actually pause for approval under Actions → the run →
"Review deployments", per the updated `docs/guides/releasing.md`.
